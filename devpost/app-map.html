Tally Up

A compact map of how the app works and where to go next — kept for your own reference, not part of the running app.

What this is

Tally Up is a phone-first expense tracker for someone already used to tracking money by hand (an Excel sheet per bank account), who wants logging a transaction to take seconds instead of becoming a backlog. It tracks multiple personal and business accounts across three currencies (NGN, USD, GBP).

Three moving pieces, each doing one job:

  • Your browser — every page is plain HTML/CSS/JS, no framework, no build step. All the logic (validation, balance math, the Excel export) runs here.
  • Supabase — the only place real data lives: profiles, accounts, transactions, plus sign-in. Every request is checked against who's signed in before anything is returned.
  • Netlify — hosts the static files and gives the app one URL that works the same on phone, laptop, or tablet.

One action, traced end to end

Logging a transaction and watching the balance update

The route we walked through together: the number on screen is never a stored value — it's recomputed fresh from starting_balance plus every transaction, every time. That's deliberate: there's no separate balance to forget to update when a transaction is added, edited, or deleted.

  1. 1 Entry point — js/transaction.js, the form.addEventListener('submit', ...) block (around line 108), which calls supabase.from('transactions').insert({ user_id, account_id, type, date, description, amount }) (around line 150). This is where a typed amount leaves the browser and becomes a saved row.
  2. 2 The math — js/account.js, renderBalance() (around line 88): starting_balance + transactions.reduce((sum, tx) => sum + (tx.type === 'inflow' ? tx.amount : -tx.amount), 0). No stored balance column anywhere — it's always arithmetic over real rows.
  3. 3 Result — same function in js/account.js writes that computed total into the page. The same pattern repeats in js/dashboard.js for the Dashboard's totals, just summed across every account instead of one.
A real bug this exposed

Every table — including transactions — carries its own direct user_id foreign key to profiles, separate from transactions.account_id's link to accounts. Deleting a test user failed twice in a row with a foreign-key error, because each relationship needed its own on delete cascade fix — the second one wasn't obvious until the first fix's error message pointed at it. Lesson: when a delete is blocked, check for every foreign key referencing that row, not just the first one you find.

To change this, start here

  • Add a field to transactions (e.g. a category tag) → add the column in Supabase, then update the insert/update calls in js/transaction.js and wherever the row is displayed (js/account.js's renderTransactionRow()).
  • Change what counts toward a balance → it all flows through the same reduce() pattern in js/account.js (renderBalance()) and js/dashboard.js — change the logic once, in both places.
  • Change a label or button's wording → it's plain text straight in the HTML files (e.g. transaction.html's #save-button) — no templating layer to go through. We tried exactly this during the walkthrough: changed "Save Transaction" to "Log It", saw it render, then reverted back.
  • Add a new page → follow the existing pattern: a plain HTML file plus a matching js/<name>.js that imports supabase from js/supabase-client.js and checks the session via js/auth-guard.js.

A practice to reuse

Decision: spec.md > Data Model deliberately says a balance is "never stored as its own number" — it's always computed from starting_balance plus every transaction. Evidence: this is exactly what renderBalance() in js/account.js does, and it's why editing or deleting a transaction never leaves a stale number behind — there's nothing cached to forget to update.

Reusable practice: when a value can be derived from other data you already trust, prefer recomputing it over storing and syncing a separate copy. It costs a little more computation, but it makes an entire category of bugs (stale caches, forgotten updates) structurally impossible — worth writing into a spec's Data Model section up front on your next project, the same way this one did.

Running it again

No build step. Open any .html file with a local static server (or just the deployed Netlify URL) — sign in, and you're on the Dashboard. See spec.md > Where It Runs and How Someone Tries It for the full setup (a Supabase project's URL/key in js/supabase-client.js, and a Netlify deploy connected to this repo).
