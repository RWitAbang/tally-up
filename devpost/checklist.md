# Build Checklist

Build mode: learn

## Slices

- [x] **1. Prove the foundation: sign in, save data, and go live**
  Becomes usable: You can open the deployed Netlify URL on your phone, sign in with the one account, and see proof that a row written to Supabase was saved and read back correctly.
  Why now: Supabase, Auth, RLS, and Netlify are all unfamiliar to you and everything else gets built on top of them. The spec's own plan is to prove this chain with a throwaway test before any real UI depends on it — bad news here is cheap; bad news three slices in is not. This also covers project bootstrapping (file structure, Git, deployment).
  PRD ref: n/a (infrastructure step named directly in `spec.md > Decisions and Open Issues`, the "one genuine uncertainty" paragraph)
  Spec ref: `spec.md > Stack`, `spec.md > Where It Runs and How Someone Tries It`, `spec.md > Components > Supabase Client & Session Guard`, `spec.md > Components > Sign In`, `spec.md > Data Model`, `spec.md > External Services and Dependencies`
  Build: Scaffold the project per `spec.md > File Structure`. Create the Supabase project with the `profiles`, `accounts`, and `transactions` tables and turn on Row Level Security per the policies described. Create the one Supabase Auth user in the dashboard. Add `js/supabase-client.js` and `js/auth-guard.js`. Build `sign-in.html`/`js/sign-in.js`. Build a throwaway `index.html` that, once signed in, inserts a dummy row into `accounts` and displays it back on screen to prove the full chain works. Push the repo to GitHub and connect it to Netlify; confirm the deployed URL loads.
  Verify (mechanical): Open the deployed Netlify URL, sign in, and confirm the dummy row appears on screen. Check the Supabase table editor directly to confirm the row landed with the correct `user_id`. Check the browser console for errors. Try an incorrect password and confirm the inline error appears.
  Learner check: On your phone, open the Netlify link, sign in, and see the proof message appear.
  Commit: `Set up Supabase, auth, and deployment; prove the connection end to end`

- [x] **2. Add your real accounts and see them listed**

  Why now: Multi-account, multi-currency, personal/business handling is the unique kernel of this app — it needs to exist before any transaction can reference an account.
  PRD ref: `prd.md > Account Setup`, `prd.md > Screens and Layout > Account Setup`, `prd.md > Every later visit`
  Spec ref: `spec.md > Components > Account Setup` (add mode only), `spec.md > Data Model > accounts`, `spec.md > The Core Journey Through the System` (steps 3-5)
  Build: Replace the throwaway `index.html` with real routing (no session → `sign-in.html`; signed in, zero accounts → `setup.html`; signed in, accounts exist → `dashboard.html`). Build `setup.html`/`js/setup.js` in add-only mode: one account at a time (Bank Name, Account Type, Currency, Personal/Business, Starting Balance), looping on "add another?" until declined. Build a minimal `dashboard.html`/`js/dashboard.js` that lists every account with an "Add Account" button. Show a simple "loading..." state while fetching.
  Verify (mechanical): Add 2-3 test accounts across both currencies and both categories. Confirm each lands correctly in the Supabase table editor. Reload the page and confirm it routes straight to the dashboard (setup does not repeat).
  Learner check: Add your real bank accounts on your phone, one at a time, and watch them appear in the list.
  Commit: `Add account setup flow and basic dashboard listing`

- [x] **3. See your real totals at a glance**
  Becomes usable: The actual "at a glance" dashboard — overall totals plus Personal and Business sections, each broken out by currency.
  Why now: This is the first screen you'll look at most, and it's one of the two things Mint and other wallet apps never got right for you.
  PRD ref: `prd.md > Dashboard`
  Spec ref: `spec.md > Components > Dashboard`, `spec.md > Data Model` (computed balance)
  Build: Extend `js/dashboard.js` to compute overall Naira and Dollar totals, then Personal and Business subtotals per currency, and group the account rows under their section.
  Verify (mechanical): Using your test accounts' known starting balances, hand-calculate the expected overall and section totals, then compare against what renders.

- [x] **4. Log a transaction and watch balances update**

## Revisions

- Added explicit `grant` statements for the `authenticated` role on `accounts`, `transactions`, and `profiles`, on top of the RLS policies from the original plan — raw SQL table creation in Supabase doesn't auto-grant table privileges the way its dashboard UI does, and the first live insert failed with "permission denied" until these were added. No change to `scope.md`/`prd.md`/`spec.md`; this is a one-time setup correction in the Supabase project itself.
- Final review, round 1 (account number, export ledger format, redirect/loading fixes): added an optional Account Number field (`spec.md`/`prd.md` updated); account type now shows in the transaction account picker and at the top of the account page, combined on one line with the bank name, with the account number on its own line beneath; adding a transaction now lands back on that account's page instead of the Dashboard; Export sheets are named by bank name + account type and lead with the account number, starting balance, and a running Balance column; replaced plain "loading..." text with a spinner. A consolidated menu was raised again and deferred again — recorded in `scope.md > Later`.
- Final review, round 2 (layout): on both the account page and the Dashboard, action buttons (Add Transaction, Back, Add Account, Export) sat after the list they belonged to, so they sank further down the page as accounts/transactions were added. Moved them to a fixed position right after the balance/totals, before the list. Introduced the first icon (a back arrow, Phosphor Icons fill style, already the stack's planned icon set from `spec.md` but not used until now) for the one clearly universal case; kept other actions as labeled buttons rather than icon-izing everything at once.
- `transactions.account_id` had no `on delete cascade`, so deleting an account with existing transactions failed with a foreign-key error in Supabase's Table Editor. Added `on delete cascade` (`spec.md` updated) — a transaction without its account has no meaning in this app, so cascading is the correct behavior, not just a workaround.
- Final review, round 3: the action buttons on the Dashboard and account page were static HTML, so they rendered immediately alongside the loading spinner, before the totals/balance had loaded — a half-ready-looking page. Wrapped each page's real content (buttons included) in a container that starts `hidden` and is only revealed once its data has actually loaded, so the spinner shows alone and the whole page appears at once.
- Netlify's "Team protection" (Visitor access) defaulted to Private, which would have blocked anyone — including the learner on their phone — from reaching the deployed site without a Netlify login. Switched Project visibility to Public in Netlify's Site configuration; the app's own Supabase Auth sign-in remains the actual access gate, unaffected by this setting.
- Dashboard listing is sorted alphabetically by bank name (not creation order) — learner preference discovered during the early checkpoint, not specified in `prd.md`/`spec.md`.
- Starting Balance now uses a custom-formatted text input (comma-grouped, capped at 2 decimals) with our own inline validation message, instead of a native `type="number"` input — the learner wanted thousands separators and a styled "Please enter a number" message, neither of which a native number input can do. Formatting was initially blur-only; the learner asked for it live as they type instead, so `js/currency.js` now also exports `attachLiveAmountFormatting()`, which reformats on every keystroke while preserving cursor position. The same helper will be reused for the transaction Amount field in Slice 4.
- Final review, round 4: Account Number field now filters to digits only as you type; added a "Delete Account" button on the Edit Account screen (uses the same cascade, so its transactions go with it); Account Number now also shows on each Dashboard row, not just the account page.
- Added a new **Account Settings** screen (name, surname, email, password) — genuinely missing before: the single login was only ever set up directly in Supabase's dashboard, with no in-app way to change it. Scoped deliberately to exclude self-service sign-up (still deferred per `prd.md`). Email changes go through Supabase's own confirm-by-link flow; `js/auth-guard.js` now re-syncs `profiles.email` from the Auth record on every page load to catch up once a change is confirmed, since there's no other way to know client-side.
- Color direction revised from "colorful and playful" to minimal with one signature accent — see `spec.md > Look and Feel` for the full reasoning. Along the way, fixed two button-hover bugs this surfaced: a generic hover rule was painting a solid color block behind icon-only and text-link buttons (the back arrow, Sign Out, Edit, Account Settings) instead of just tinting them, and an invented off-palette hover color (`#9c2b5a`) was replaced with literal sky blue.
- Attempted to left-align button text to fix a perceived mismatch between left-aligned headings (e.g. "History") and the buttons below them. The learner didn't want that — button box edges were already aligned with the headings; only the centered *text* inside the buttons sat further right. Reverted; left unresolved pending a clearer description of what should change.
- Added pagination to an account's transaction history, 10 per page, once requested — numbered page buttons, prev/next, and swipe (tested both directions via simulated touch events). Not in the original `prd.md`/`spec.md`; added because a long history would otherwise require endless scrolling. Caught and fixed a real bug while building it: `PAGE_SIZE` was declared after the code that used it, which would have broken history display entirely (a `ReferenceError`, not just a cosmetic issue) — moved the declaration to the top of `js/account.js`.
- Added two more account types, Utility Card and Domiciliary Card, alongside the original three — required widening Supabase's `account_type` check constraint and adding the options to Account Setup. Introduced `js/account-types.js` as a shared label map (`utility_card` → "Utility Card") used by the account page, Dashboard rows, and the transaction form's account picker, replacing three separate ad-hoc capitalize-the-first-letter calls that would have mangled multi-word, underscored type names.
- Closed a real gap flagged during review: Edit Account and Edit Transaction had no loading or error state around their data fetch — a slow or failed request would show a blank or broken form with no explanation, unlike every other page. Both now show a spinner while loading and "couldn't load — try again" (form hidden) on failure, matching the rest of the app and the failure-mode rule already in `spec.md`.
- Added `404.html` at the project root — Netlify serves this automatically for any unmatched route. Can't be tested against the local dev server (that behavior is Netlify-specific), only verified by opening the page directly.
- Three proactive UX suggestions, all agreed and built: (1) the transaction form's account picker now defaults to a "Select an account" placeholder instead of silently defaulting to the alphabetically-first account, so a transaction can't land against the wrong account by accident — found and fixed a real bug while building this, where the `<select>`'s native `required` attribute was silently blocking our own validation message before it ever ran, the same native-vs-custom-validation issue we'd already hit once before with Starting Balance; (2) Save buttons on Account, Transaction, and Account Settings forms now disable and show "Saving…" while a request is in flight, preventing duplicate submissions on a slow connection — verified by firing two rapid clicks programmatically and confirming exactly one row was created each time; (3) an empty Dashboard section (e.g. zero Business accounts) now shows "no business accounts yet" instead of just a bare heading and subtotal, matching the existing "no transactions yet" pattern.
- Replaced the browser's native `window.confirm()` for deleting an account or a transaction with a custom in-app dialog (`js/confirm-dialog.js`) styled to match the app, since a plain system popup looked out of place next to everything else. As a side benefit, this is no longer subject to the native-dialog auto-decline this build environment applies — both the cancel and confirm paths were verified by actually clicking through the real buttons, for both account and transaction delete. The duplicate-account warning in Account Setup still uses the native `confirm()`; left as-is since only delete actions were in scope for this change.
- Final review, round 6: the delete-account confirmation now includes the account number when set (e.g. "Delete GT (1234567123)?"), so it's clear which same-named account is being removed; "Done — go to Dashboard" became "Done! — go to Dashboard"; added a "Cancel" button to Account Settings (previously only the header's back arrow). Added Pound as a third currency, alongside Naira and Dollar — required widening Supabase's `currency` check constraint, a new option in Account Setup, and replacing `dashboard.js`'s hardcoded two-currency totals with a currency-agnostic version driven by a shared list in `js/currency.js` (`CURRENCIES`, `currencyLabel()`, `currencySymbol()`), also now used by `account.js` instead of its own inline ternary.
- Found and fixed a real overflow bug while adding Pound: the Dashboard's total cards used `flex: 1` with no `min-width` or wrapping, so a long unbroken amount (no spaces to break on) forced the flex item wider than its share and spilled past the card edge rather than wrapping — classic flexbox `min-width: auto` gotcha, and exactly what the learner's screenshot showed. Fixed with `flex-wrap: wrap`, an explicit `min-width: 0`, and `overflow-wrap: break-word` on the amount text, applied to both the Dashboard total cards and the single account-balance card. A separately reported "Account Settings / Sign Out not aligned on the right" turned out, after precise pixel measurement, to not be a real alignment bug (both ended at the exact same x-coordinate) — likely the same overflowing total visually throwing off the whole top-right area; resolved itself once the overflow was fixed, pending the learner's confirmation.
- Final review, round 7: reworked the Dashboard totals layout on the learner's request — Naira full-width at top (the home currency), Dollar and Pound side by side below, instead of three equal-width cards. Caught a second real flexbox bug while building this: the primary (Naira) card shared a `flex: 1 1 130px` rule meant for the row of secondary cards, but inside a *column* flex container that same rule sets a minimum *height* instead of width, so the card was stretching taller than its content needed — fixed by giving the primary card its own `flex: 0 0 auto`. Replaced text-wrapping with an actual auto-shrink: `js/fit-text.js` (`fitText()`) measures rendered width after render and reduces font-size in steps until the amount fits on one line, down to a floor of 0.8rem, used on both the Dashboard totals and the account-balance card. Verified by inserting a 14-digit test balance — confirmed it fits at full size in the wide primary card, and visibly shrinks in the narrower secondary cards; at a deliberately absurd trillion-dollar test value it still clips once it hits the minimum floor, which is an acceptable boundary for amounts this app will never realistically see. Totals remain sky-colored for now; recommended keeping it that way (hierarchy already comes from size and position, and a second hue would work against the single-accent-color direction from the earlier color review) but this is pending the learner's confirmation, not yet a settled decision.
- Final review, round 8: confirmed Pound shrinks using the exact same `fitText()` call as Dollar (verified live with a trillion-pound test value) — they already shared one mechanism; each just shrinks independently based on its own content length, which is correct. Extracted the transaction-history pagination (built in an earlier round) into a shared `js/pagination.js` (`createPaginatedList()`) so it could be reused rather than rewritten, then applied it to the Dashboard's Personal and Business account lists at 6 per section, with page buttons, prev/next, and swipe — same pattern, same code, two places. Refactoring the existing transaction-history pagination onto the shared helper was verified as a non-regression by re-testing it directly (15 test transactions, confirmed still 2 pages of 10, newest-first) before trusting the shared code for the new use. Presented two mockup options for differentiating the Naira card from Dollar/Pound using tints of the existing sky blue rather than a new color — awaiting the learner's pick.
- Final review, round 9: learner picked the darker-Naira option (new `--sky-dark` token, `#048AA8`, used only on the primary total card) over lightening the secondary two. Each total's label now also carries its currency symbol — "Total Naira (₦)", "Total Dollar ($)", "Total Pound (£)" — matching the convention Account Setup's currency dropdown already used.
- Final review, round 10: an automated monthly email backup was requested, then deferred to `scope.md > Later` after discussion — it would be the project's first real backend piece (a scheduled function plus a separate email-sending service), out of step with the rest of this build. The Excel export's downloaded filename now includes today's date (`YYYY-MM-DD_TallyUp_Export.xlsx`). Fixed by tracking whether the cursor is before or after the decimal point separately from digit-counting.
